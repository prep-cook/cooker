Changed

- `POST /v1/images/generations` and `/v1/images/edits` send nothing until the upstream answer holds an image, so an upstream failure or an answer without an image moves to the next credential. The response carries `X-Ck-Stream-Id` and `Cache-Control: no-store`, has no `Content-Length` and no keepalive comments, and a streamed response resumes with `GET /v1/streams?after=v1.e.<events>`. An upstream error before the first image is returned with its own status instead of a 200 that ends in an `error` event.
- xAI image requests keep every aspect ratio xAI documents and the `1.5k` resolution. A request naming both `image` and `images`, a ratio or resolution xAI does not document, or `quality` for xAI is refused with 400 before anything is sent.
- xAI image results keep `mime_type`, `file_output` and `storage_error`.
- An image edit form whose `stream` is not `true` or `false`, whose `n` is not a number, or whose file part has no `Content-Type` is refused with 400.
- xAI image requests take `deferred`, `storage_options` and `output`; any other image provider refuses a request carrying them before anything is sent. `deferred: true` with `stream: true` is refused with 400. A deferred request is answered with URLs: without `response_format` it asks xAI for `url`, and `b64_json` is refused with 400.
- A deferred xAI image request answers `{"request_id":…}`. `GET /v1/images/{request_id}` polls it on the credential that created it: 202 with xAI's body while it runs (also when xAI's 202 has no body), then the Images response, or 200 with xAI's `error` body when the job failed. Only the client key that created the job can poll it; any other key, an expired job (3 hours after its last poll) or a video job id gets 404 with nothing sent.
- A deferred image job's usage is recorded once, at the first finished poll that reports it.
- Deferred image jobs share the video job table: when 4096 jobs are tracked, a deferred image create is refused with 503 (`image_jobs_full`) before anything is sent.
